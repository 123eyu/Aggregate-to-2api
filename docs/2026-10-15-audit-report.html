03做了什么：五个真缺陷

P1 · 静默失效

定时清理循环每次都在中途抛异常，后半段从未执行

api/bg_tasks.py 的持久化队列清理写的是 _engine._queue_db，而 _engine 是第 43 行 from .worker import engine 导入的模块；_queue_db 却是 Engine 的实例属性。

$ python -c "import api.worker.engine as m; print(hasattr(m,'_queue_db'))"
False        # 模块上没有 → 每次必抛 AttributeError

异常被第 142 行 except Exception 吞成 warning。但它抛在 try 块的中部， 所以第 72 行之后的所有清理逻辑（DAG TTL、告警评估）每次都被跳过。

修法：改从 api.meta 取 Engine 单例（与 lifespan 注入的是同一个实例）+ 防御式 getattr。

P1 · 整条流水线

CI 前端门禁持续红：测试套件存在系统性 DOM 泄漏

通过 GitHub API 取到失败 job 的真实 annotations —— 不是单个用例的问题，而是多个文件同时报错：

CostsPage.test.tsx      → Found multiple elements with role "button" and name "按模型"
CommandPalette.test.tsx → Found multiple elements with role "combobox"
                        → Found multiple elements with role "dialog"
多个文件                 → Found multiple elements with role "button" and name "确认"/"提交"

根因很讽刺：frontend/vite.config.ts 设了 isolate: false， 并在注释里声称「测试间通过 src/test/setup.ts 的 beforeEach 清理」—— 但那个文件从来没有任何清理逻辑。注释描述了一个不存在的行为。

修法：在 setup.ts 显式注册 afterEach(cleanup)（vitest 对 isolate:false 的官方配套做法），并把配置注释改成与实现一致、标注"配套关系"。

P2 · 静默降级

多订阅者场景下，谁先断开就清掉所有人的回放缓冲

sse_events.py:246 和 ws_events.py:125 的连接收尾都无条件调 clear_task。 同一任务被 2 个客户端订阅时（多标签页、或重连旧连接未断），先断开的一方会清掉共享的事件缓冲， 另一方之后用 Last-Event-ID 重连拿不到任何历史，而且不报错。

修法：新增 clear_task_if_idle，把"判空"和"清理"放进同一把锁（避免 check-then-act 竞态），两处调用点改用它。

P2 · 契约盲区

环境变量映射的校验有个结构性漏洞

test_config_validate.py 的既有双向校验用 regex 扫源码文本找 validation_alias="IF_X" 字面量。 盲区在于：没有 alias 的字段根本不进集合 —— 于是"字段存在、但 env 永远读不到"这类缺陷对它完全不可见。

实证：Settings.user_agent 是 202 个字段里唯一漏挂 alias 的。

修法：新增基于运行时 model_fields 反射的契约测试 + NO_ENV_BY_DESIGN 显式登记表。 新增字段若忘记挂 alias，测试立刻红，强制作者做显式决策。

P1 · 文档说谎

覆盖率门槛文档写 70，CI 实际卡 80

ci.yml:53 与 deploy.yml:30 都是 --cov-fail-under=80， 而开发文档（SKILL.md、imagefree-rules.md）写的是 70%。

危害很具体：开发者按文档自测 70% 通过，推上去撞 80% 意外失败。 根源是 v7.6 把门槛从 70 统一到 80，文档没跟上。

04更重要的：我差点修错的东西

审计子代理报了一条"P1"：.env 里的 IF_WORKERS=10 被静默覆盖成 48， 建议改用 model_fields_set 修。

我按惯例自己复现了一遍，结果把它否掉了：

IF_WORKERS=10  IF_WORKERS_MAX=16  IF_TOKEN_POOL_SIZE=6  IF_MAX_QUEUE=2000

start.ps1:75      & $py -m uvicorn api.main:app ...   # 不加载 .env

真相是：.env 压根不会被读，而不是"读取后被覆盖"。 哨兵逻辑本身是正确的 —— 我用真实环境变量验证过（IF_WORKERS=7 → workers=7 ✓）。 生产走 docker env_file: / systemd EnvironmentFile= 时会注入 os.environ，工作正常。

我会改掉一段本来正确的哨兵逻辑，换来一个看起来专业、实际无用的 diff， 并且顺手把线上并发从 48 掉到 10 —— 而这种行为变更根本解决不了任何真问题。

这类"伪造工作量"是本批刻意避免的。同类判定还有 4 项， 包括"生产模板只列 42/201 个配置项"（正常设计，且实测零幽灵键） 和"三处 except TimeoutError: pass"（断言本就在 try 块外，判别力完整）。

08这一批的元教训

  1. 静态扫描会骗人，实测不会。 三次误判全出自"看代码下结论"。方法级 curl、真跑测试、变异验证 —— 这三样才是证据。
  2. "没崩"和"没问题"是两回事。 1790 次压测请求 0 个 5xx，但同期暴露出"清理循环每次中途抛异常"。存活证明不等于健康证明。
  3. 注释会说谎，而且没人发现。 这一批抓到的核心问题里，有三个是"文档/注释描述了一个不存在的实现"（setup.ts 的清理、.env.example 的修改指引、覆盖率门槛 70 vs 80）。注释漂移是会直接导致 CI 红的。
  4. 拒绝伪造工作量。 审计报了 8 条"问题"，其中 4 条经实测是伪问题。把伪问题修掉比不修更糟 —— 它污染 diff、掩盖真问题、还可能改动生产行为。

09测验

10 道题，覆盖本批的每个关键判断。展开看答案。全部答对才说明你真的读懂了这批变更。

Q1 · bg_tasks.py 那个 P1 为什么"比看起来更严重"？

因为它不止让 queue.db 永远不被清理。异常抛在 try 块中部， 被外层 except Exception 吞掉后直接跳到末尾 —— 于是它后面的所有清理逻辑（DAG run TTL 清理、告警评估 evaluate）每一次都被跳过。 一个看起来只影响队列的 bug，实际让整个定时维护循环的后半段长期失效。

Q2 · 为什么给 bg_tasks 的回归测试必须用 AST，而不是字符串匹配？

因为字符串匹配会被改名绕过。第一版我断言"源码里不出现 _engine._queue_db"， 但变异成 _engine_inst._queue_db 时测试照样通过（字符串对不上）， 而且断言本身还被我自己修复处的解释性注释误伤。 改用 AST 定位"对 _queue_db 的属性访问节点"后，两种变异（裸属性访问、回退旧写法）都会被抓。

Q3 · CI 前端失败的真根因是什么？为什么说"注释说谎"？

根因是 vite.config.ts 设了 isolate: false，但没有配套的 DOM 清理， 导致测试之间组件残留、getByRole 命中重复元素。"注释说谎"指的是：配置注释声称 "测试间通过 src/test/setup.ts 的 beforeEach 清理"，而 setup.ts 里根本没有任何清理逻辑 —— 它只做了导入 jest-dom 和补 localStorage 两件事。注释描述了一个不存在的实现。

Q4 · 我为什么没有去修".env 的 IF_WORKERS 被覆盖"那条 P1？

因为复现后发现它是误诊。三个事实：
① 那些字段的库默认值恰好就是 .env 里写的值（10/16/6/2000），所以之前".env 生效"的观测其实是默认值；
② Settings.model_config 里 env_file=None，全仓无 load_dotenv 调用，start.ps1 直接起 uvicorn 不加载 —— .env 根本不被读取；
③ 哨兵逻辑本身正确：真实环境变量 IF_WORKERS=7 实测生效为 7。
所以正确的动作是不改。改了会得到一个无用 diff，还会把线上并发从 48 变成 10。

Q5 · SSE 那个修复，我的第一版测试为什么是伪测试？怎么补救的？

第一版测试直接调 hub.clear_task_if_idle(...)，验证的是方法本身。 变异测试把调用点（task_events_generator 的 finally）改回无条件 clear_task 时， 测试照样全绿 —— 也就是说修复被回退也检测不到。
补救：补两条"调用点契约"测试，用 AST 断言生成器里调的是 clear_task_if_idle、且不直接调 clear_task； 再加一条扫 ws_events 的非注释代码。之后变异立刻被抓。

Q6 · env 映射契约的"结构性盲区"具体盲在哪？

既有校验用 regex 扫源码文本找 validation_alias="IF_X" 字面量来做双向比对。 盲区是：没有 alias 的字段根本不会进入那个集合，所以"字段存在、但环境变量永远读不到" 这类缺陷对它完全不可见。实证就是 Settings.user_agent —— 202 个字段里唯一漏挂 alias 的。
新契约改用运行时 model_fields 反射，并要求无 alias 的字段必须登记进 NO_ENV_BY_DESIGN 并写明理由。

Q7 · 覆盖率门槛 70 vs 80 的失实，实际会怎么伤人？

开发者按文档（70%）自测通过 → 推上去撞 CI 的 80% → 意外失败， 而且会误以为是自己的代码有问题，而不是文档过时。根源是 v7.6 把门槛统一到 80，文档没同步。 本批修了 4 处（只改 .claude/skills/ 下的权威副本；.agents/ 是未入库的旧镜像，不动）。

Q8 · 为什么说"本地 299 passed"不能证明前端修复有效？

因为变异测试给了反证：把我加的 afterEach(cleanup) 摘掉，本地跑仍然 28 文件 / 299 用例全绿。 说明本机环境下 RTL 的自动清理是生效的、复现不出 CI 的症状 —— 根因机制在 CI 上成立，但本机无法判别。 最可能的环境差异是 CI 用 Node 20、本机用 Node 25.8.1。
结论：这个修复必须靠推送后重跑 CI 确认，在那之前只能算"按最佳实践施加"，不算"已验证"。

Q9 · 本机前端测试套件此前跑不起来，真正的原因是什么？

NODE_OPTIONS=--max-old-space-size=512 —— 这个项目调优建议里的值太小， vitest worker 起不来（先是 Timeout waiting for worker to respond，后是 Worker exited unexpectedly）。 改成 4096 后立刻跑出 28 files / 299 tests 全绿。
教训：文档里的"性能调优"参数，可能正在阻塞测试基建本身。

Q10 · 这批最反直觉的一条元教训是什么？

可能是这一条：文档/注释漂移会直接导致 CI 变红。
本批五个核心问题里，有三个本质是"有人写下了与实现不符的描述"：setup.ts 声称的清理、 .env.example 指错的修改文件、覆盖率门槛 70 vs 80。 它们都不是"代码写错了"，而是"说的话和做的事不一致" —— 而后者更难被发现，因为没有人会去验证一条注释。
