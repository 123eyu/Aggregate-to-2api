02真根因：判据与被判据的对象，不是同一次读取

把 IPBlocklistStore 的逻辑摊开看，缺陷一眼就能看出来 —— 但我们之前一直在盯错的地方：

旧实现（有缺陷）

async def init_schema(self):
  if self._initialized: # 读「标志」
    return
  ... 建表 ...
  self._initialized = True

async def add_or_update(self):
  await self.init_schema()
  conn = await self._get_conn()
  # ↑ _get_conn 读「另一个属性」_path
  await conn.execute("INSERT ...")
修法（本轮）

async def init_schema(self) -> str:
  path = self._path # 单次快照
  if self._initialized_path == path:
    return path
  ... 在 path 上建表 ...
  self._initialized_path = path
  return path

async def add_or_update(self):
  path = await self.init_schema()
  conn = await self._get_conn(path)
  # ↑ 建表与连接用同一个 path

缺陷可以一句话说清：用布尔 _initialized 判断「表建过没」，却用 _path 去连接。 两者之间没有任何绑定关系。只要 _path 被换掉而标志仍是 True， 写入就会落到一个没建过表的新库上 —— 于是 no such table。

为什么「等后台任务」治不了它

能把标志置回 True 的协程不止一个。这个项目里至少有两处会在旧路径上跑 init_schema()：

  • api/request_guard.py 的 _sync_blocklist_cache（定期全量同步封禁缓存）
  • api/bg_tasks.py 里的 ip_blocklist_store.count()（告警上下文统计）

它们和「测试 fixture 有没有把任务排空」完全无关。所以根因与「等不等」无关 —— 这是上一轮判断失误的核心。

03第二处根因：一个等不到的裸 task

既然想到了「排空后台任务」，那就有个前置问题必须验证：排得掉吗？

答案是排不掉。background.await_pending() 只看得见 background.spawn 注册过的任务；而 _sync_blocklist_cache 当时用的是：

// api/request_guard.py —— 旧写法（裸 task）
loop = asyncio.get_running_loop()
loop.create_task(_sync_blocklist_cache())   ← 不注册进任何注册表

// 同一个文件里，另一个同类调用点早就改对了：
spawn(_auto_block_ip(ip, reason), name="auto_block_ip")   ← 走 spawn

这是个漏改的同类点：同文件、同性质（fire-and-forget 写）、同一个作者早就把另一处改成 spawn 了。裸 task 不只有「等不到」的问题，还有 asyncio 官方文档点名的 「循环只持弱引用，中途等 I/O 的 task 可能被 GC 静默取消」—— 表现就是封禁缓存不同步。

已修

教训：「等一等」型修复，要先验证「等得到吗」

我加了一个排空函数，却没先确认目标任务是否在那个集合里。这是典型的 凭直觉假设工具覆盖面。教训记进 .wolf/cerebrum.md： 新增后台任务一律用 background.spawn；使用排空类工具前先确认对象的注册方式。

04确定性复现：不靠碰运气

flaky 最怕「改完跑几次是绿的就说修好了」。所以第一步是做确定性复现 —— 代码里构造出那条竞态路径，让它每次必炸：

# 复现脚本（修复前）
s = IPBlocklistStore(db_path=p_old)
await s.init_schema()        # p_old 建表，_initialized = True
s._path = p_new              # 只换路径，不动标志 ← 缺陷触发点
await s.add_or_update(...)
# → sqlite3.OperationalError: no such table: ip_blocklist

报错与 CI junit 逐字一致。在途版本（原 TOCTOU 时序）同样命中：

await s._write_lock.acquire()                    # 占住写锁
t = asyncio.create_task(s.add_or_update(...))
await asyncio.sleep(0)                           # 让它越过 init_schema、卡在锁上
s._path = p_new                                  # 换库
s._write_lock.release()
await t                                          # → 同一条报错

07沉淀：这个坑的通用形状

写进 cerebrum

四条可复用的判断

  1. 「布尔标志 + 另一个属性」是 TOCTOU 温床。 看到 if self._flag: 后面紧跟用 self._另一个属性 干活 → 立刻怀疑。 判据与被判据的对象必须是同一次读取（此处：把判据换成路径快照，并让建表函数返回它用的路径）。
  2. 「等一等」型修复要先验证「等得到吗」。 裸 asyncio.create_task 不注册进任何集合，排空工具对它无能为力。
  3. 先分清失败路径是「直连」还是「后台任务」再定修复方向。 前者与排空、与 task 生命周期都无关。
  4. 本项目的 junit classname 会误归因（本次指向完全不相干的文件）， 必须以 traceback 的 frames 为准。

修复点在被共享的对象内部，而不是「要求调用方更小心」—— 这是这次修复与上一轮最本质的差别。受共享状态影响的对象，应该自己保证不变量， 而不是把正确性外包给每一个调用者。

测验：你真的读懂了这个 bug 吗？

八道题，覆盖根因、修复取舍、验证方法与这次的方法论教训。 答案藏在折叠里 —— 先自己想，再点开对。

Q1. 旧代码里，什么条件下会出现 no such table: ip_blocklist？

当 _initialized 为 True（认为表已建）而 _path 指向一个从未建过表的库时。init_schema() 会因为标志为真直接短路返回， 随后 _get_conn() 用新 _path 连到空库，INSERT 就炸。

关键：这两个属性之间没有任何绑定，所以「标志为真」不蕴含「这个库有表」。

Q2. 为什么上一轮的「排空后台任务」修法无效？

两个独立原因，任一都足以让它无效：

  • 失败发生在测试进程的一次直连调用（store.add_or_update）， 不经过任何后台任务 —— 排空与这条路径无关。
  • 即便真的是后台任务，_sync_blocklist_cache 当时用裸 create_task， 不在 background._BACKGROUND_TASKS 里，await_pending() 也看不见它。
Q3. 为什么把判据从「布尔标志」改成「路径快照」能根治？

因为它把「是否已建表」这个判断绑定到了具体的库。 检查变成 self._initialized_path == self._path —— 路径一换，等式不成立，短路自然失效 → 重走建表。缺陷不再可能发生，而非「概率降低」。

Q4. 为什么还要让 init_schema() 返回路径，而不只是改判断条件？

因为「检查/建表用的路径」与「随后读写用的路径」若分两次读 _path， 中间仍会留一条缝（换库发生在两次读之间）。让 init_schema() 返回它实际建表的那个路径， 调用方用返回值开连接，就保证了两者是同一次读取。 压测里 in_flight 场景在只做前半段修复时仍能通过，正是这第二道防御在起作用。

Q5. 变异验证里第 3 个测试（切库隔离）在缺陷版下也通过 —— 这是缺陷吗？

不是，那是设计如此。它是对照项，作用相反：防止有人用「永远使用同一个库」 的方式让前两个测试变绿（那会破坏多库语义，是假修）。一个测试不一定要「抓住 bug」， 也可以「钉住不变量」。所以变异后是 2/3 红，而不是 3/3。

Q6. 为什么 CI 变成绿色，仍不足以单独证明修好了？

因为这条 flake 是间歇性的 —— CI 历史里 success 与 failure 交错出现， 一次绿可能只是没踩中触发窗口。充分的证明需要： 确定性复现（旧码必炸、新码必过）+ 变异验证（退回修复测试就红） + 多次压测。CI 绿是确认，不是唯一支柱。

Q7. 这次的修复点为什么放在 store 内部，而不是「让 fixture 更小心」？

因为共享状态的正确性不能外包给每个调用者。 能把 _initialized 置回 True 的协程很多 （_sync_blocklist_cache、bg_tasks 的 count()…）， 调用方无论多小心都堵不住。受共享的对象应自己维护不变量 —— 这也是为什么上一轮「让 fixture 排空任务」的方向本质上是错的。

Q8. 这份报告里，哪个「事实」最容易被误读，需要特别警惕？

junit 的 classname。它把失败标成了 test_account_fsm_self_heal —— 一个毫不相干的文件。 如果按 classname 去查，会在错误的文件里浪费大量时间。 必须以 traceback 的 frames 为准。 类似的「看起来权威但会骗人」的信号还有：注释（本项目已发现多次「注释撒谎」）、 以及「跑一次是绿的」。
