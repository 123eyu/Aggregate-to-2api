接手时工作区处于一个**未提交的中间状态**：

审计结论：不是删档冒充完成。代码痕迹证明施工真实发生过（.gitignore 里的 v22 P0-4 注释、ci.yml 里的 v22 P1-2 门禁、restore_drill.py 的 200+ 行真实实现）。指南自己也把未竟项标为 ⬜，没有虚报。
但真正的风险恰好相反：api/config/constants.py、settings_core.py、tests/test_config_pkg_attr.py 三个文件**全部 untracked**。一次 git clean -fd 就会让整套拆分（含 1000 行代码 + 13 个契约测试）无声蒸发，而 HEAD 上的 __init__.py 仍是 850 行旧版 → 直接 ImportError。

② 直觉 / 审计发现了什么

发现 1：ruff 基线声明与事实不符

.wolf/memory.md 写「ruff 我改动文件 0 error」，实测：

$ ./.venv/Scripts/python.exe -m ruff check api/ tests/ scripts/
Found 27 errors.
$ echo $?
1

其中 一个是真缺陷，不是风格问题：

tests\test_uptime_probe.py:23:23: F821 Undefined name `ModuleType`

代码写 def _load_probe() -> "ModuleType":，但只 import importlib.util，从未导入 ModuleType。字符串注解会在 typing.get_type_hints() 时抛 NameError。

发现 2：移动端 E2E 从未真跑通过

scripts/e2e_mobile_smoke.cjs 默认连 127.0.0.1:4590，但**仓库里没有任何脚本在该端口提供服务**。更糟的是它写死了宿主绝对路径：

require('C:/Users/.../Desktop/imagefree-2ai/frontend/node_modules/playwright-core')
//                        ^^^^^^^^ 与当前仓库路径 (Desktop/2api目录/...) 不同

换机或改目录名即崩。而且 v22 指南承诺测 / 与 /admin 两条路径，实际只测了 /。

发现 3：真实浏览器截图暴露两个用户可见缺陷

把 E2E 真跑起来后，截图直接暴露了断言查不出的问题：

  • 门户画廊区域显示 Unexpected token '<', "<!DOCTYPE "... is not valid JSON —— 技术黑话直接渲染给用户
  • 管理端 375px 下顶栏「控制台」被压成竖排，与标题重叠
「无横向滚动」这类断言查不出这两种问题：前者不含布局溢出，后者元素没撑破容器、只是内部文字互相挤压。

发现 4：测试套件里有「看不见的失败」

分批跑全量时，几个批次超时，但其尾部输出里**残留着 F 符号**：

exit=-9 (TIMEOUT)  ...F........ [ 85%]     ← 有失败，但没超时前就出现了
exit=-9 (TIMEOUT)  ..F...                   ← 同上

第二次**完整跑到 100%** 的全量运行也证实：49%: F 55%: F 61%: F 68%: F 83%: E —— 4 个失败 + 1 个错误，而项目记忆写的是「169 关键回归全绿」。

为什么长期没被发现：失败是静默的。
tests/conftest.py 的 pytest_sessionfinish 调 os._exit(exitstatus) （Windows 本地 teardown 永不返回的兜底）。它在 terminal reporter 写失败详情之前结束进程：
· stdout 只有 .....F... 进度点，看不到用例名与 traceback
· --junitxml 也不生成文件（junitxml 插件同样在 sessionfinish 写盘）—— 已实测
所以全量跑只会告诉你"有 F"，永远不会告诉你是谁、为什么。

已定位 2 处（均修复）：

用例根因性质
test_http_pool_config.py::
test_env_overrides		 用 importlib.reload(api.config) 期望 env 生效。拆包后常量由 constants.py 在 import 期绑定为快照，而 reload 包不会重新执行已导入的子模块，故快照保持旧值（旧版常量内联在 __init__.py，reload 恰好能刷新——属偶然而非契约） 拆包引入的真回归
test_mcp_server.py::
test_tools_list_whitelist		 白名单停在 v16。v18 P1-3 在 api/mcp/tools.py 有意新增 retrieve_tools/describe_tool（intent=read、expose=True 的渐进暴露），断言未同步 陈旧断言

修 test_env_overrides 时按项目文档化设计改成子进程验证（与生产路径一致， env 在 import 前设定），而非改实现去迁就一个已放弃的 in-process reload 机制。

发现 5：前端测试套件此前完全跑不起来

Landing 的 vitest 我早先已修。管理面板（frontend）的 vitest 同样中招，而且更彻底：

$ cd frontend && npm test
 Test Files  no tests
      Tests  no tests
     Errors  28 errors        ← 28 个 worker 全部启动失败
   Duration  122.32s

Caused by: Error: [vitest-pool-runner]: Timeout waiting for worker to respond
  ❯ ../../../2api%E7%9B%AE%E5%BD%95/imagefree-2ai/...   ← 路径被 URL 编码

0 个测试执行。项目记忆写的是「vitest 串行 296/296 全绿」——那是仓库移入 2api目录 之前的结论，之后无人复跑。

修复过程中的三步（每一步都被实测否定过）：
  1. isolate:false + pool:'threads'（landing 的解法）→ 仍失败： Worker exited unexpectedly。原因是关隔离后模块挤在同一进程，撞上项目全局 NODE_OPTIONS=--max-old-space-size=512 而 OOM。
  2. 加大内存 → 跑起来了，但 296 passed / 3 failed，全是 Test timed out in 5000ms （关隔离后 setup 累计 1037s、environment 1099s，5s 超时不够）。
  3. 最终：pool:'forks'（独立子进程各有独立堆）+ testTimeout/hookTimeout: 20000 → 28 files / 299 tests 全绿，69s。
坑中坑：我中途写过一个 test.poolOptions.forks.execArgv 想直接给 worker 传内存参数—— 跑起来打出了 DEPRECATED test.poolOptions was removed in Vitest 4，该配置被忽略， 内存参数根本没生效（真正起作用的是 forks）。这种"看起来配了其实没配"的项最容易让人误判， 已在配置文件里明确标注禁用。

第 0 项是本批最重要的发现 —— CORS 白名单从未生效。
api/main.py:128 挂载中间件时读 config.CORS_ORIGINS，而该值来自 constants.py 里一行硬编码字面量 CORS_ORIGINS = "*"（同文件其他常量都是 = settings.xxx）。Settings.__init__ 里虽有 global CORS_ORIGINS; ... = self.if_cors_origins or "*"，但拆包后它只写 settings_core 命名空间，与包命名空间无关。

成因判定：既有缺陷，非本批拆分引入。HEAD 旧版中二者同处 api.config 命名空间，但模块级字面量（L817）在 settings = Settings()（L603）之后执行 → 仍把 env 值覆盖回 "*"。 净效果相同：IF_CORS_ORIGINS 一直是无效的。
