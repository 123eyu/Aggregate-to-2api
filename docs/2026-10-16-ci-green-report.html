02直觉：为什么 flaky 比崩溃更难修

崩溃会给你堆栈。flaky 不会 —— 它只给你「这次红了、上次是绿的」，然后你要在两种可能里选：

  • A：代码真有缺陷，只是触发条件苛刻
  • B：环境/时序问题，代码没错

选错方向的代价极不对称：把 A 当成 B → 缺陷一直留着；把 B 当成 A → 你去「修」一段本来正确的代码，diff 看着很专业，实际是**伪工作量**。

我在这条 flaky 上先选了 B，而且公开说了「本机无法复现，所以不做投机修改」。那句话本身没错（不臆测是对的），但它让我在**能复现却没想到方法**时过早收手。真正让我找到答案的是换了个思路：不是等它自然复现，而是强制构造触发条件。

03根因：`isolate: false` 让 mock 跨文件串味

P1 · 核心

机制

isolate: false 让同一 worker 内的多个测试文件共享模块实例， 而 vi.mock 的假模块是按文件注册的 —— 后跑文件里被缓存的组件闭包 仍指向上一个文件遗留的 mock 实例，本文件新注册的 mock 对它完全无效。

强制两文件同 worker 连跑（--no-file-parallelism）的实测：

GalleryAlbum → Gallery ：
  Gallery.test.tsx 4 用例全红
  TestingLibraryElementError: Unable to find an element with the alt text: test prompt
  （DOM 里其实是 GalleryAlbum 的 2 项数据）

Gallery → GalleryAlbum ：
  GalleryAlbum 7 用例全红
  Cannot read properties of undefined (reading 'total')

这两个文件是全仓库唯一「同一组件 + 同一 vi.mock 目标」的组合 （单 worker 全量实测 2 failed | 26 passed，失败仅此一对）。

这如何解释「同一 commit 时红时绿」

文件→worker 的分配取决于哪个 worker 先空闲。CI runner 只有 4 vCPU， 两个 Gallery 文件偶尔落进同一 worker → 后跑者必红。 本机 16 vCPU 几乎不会同组 —— 所以本地长期复现不到。

修法：不是关隔离，而是开隔离 + 降并发

我一开始差点走错方向 —— 原注释写着「关隔离是为了绕开非 ASCII 路径下 worker 启动超时」， 顺着这条线很容易得出「那就继续关着」。但**关隔离正是病根**。实测两条路的代价：

配置结果
isolate: false（原）默认并发能跑，但跨文件 mock 串味 → CI 间歇红
isolate: true + 默认并发28 errors / 0 tests（全部 worker 启动超时，套件完全不可用）
isolate: true + maxWorkers: 228 files / 300 passed（稳定可跑）

所以两处必须同时改，且 maxWorkers 写进配置（不依赖 CLI 参数，否则 CI 不受益）。

04顺带发现：进度条每 2 秒被抹回「运行中」

P2 · 用户可见

数据模型层面的不一致

后端把任务阶段发两条路，但只有一条带细节：

通道带 status_detail/progress？
SSE（api/worker/engine.py 发布）✅ 带（queued=5 / solving=30 / generating=80）
GET /v1/tasks/{id}（响应模型 TaskInfo）❌ 不带（DB 层也从未持久化）

前端两条路都订阅。于是：

  1. SSE 推 solving/30 → 进度条显示「求解中 30%」
  2. 2 秒后轮询返回 processing → 映射出 {null,null} → 被清回「运行中」+ 无定值进度条

用户看到的就是进度条每 2 秒跳一次。

修法：轮询的职责是「探测终态 + 无 SSE 时兜底」，不是用粗粒度信息覆盖精确信息：

// 状态变了要更新；状态没变且映射不出更细的阶段 → 不动现有精确值
if (mapped.statusDetail === null && lastAppliedStatus === t.status) return;

这个前提我用真实订阅验证过（不是读代码推断）：

$ 建任务 → 订阅 /v1/tasks/{id}/events
收到 data 帧: 4
status_detail 取值: ['error', 'queued', 'solving']
progress      取值: [5, 30]
✅ SSE 确实携带 status_detail/progress —— 前端修复的前提成立

05方法：变异测试救了我两次

「加了测试」和「测试能抓住这个 bug」是两件事。本批我每写一个回归锁都做变异测试 —— 把修复改回去，看测试是否真的会红。它抓出了我两个问题：

自我纠错

① 进度条那条测试，第一版是伪测试

第一版直接调 hook 的方法验证行为 —— 但变异的是调用点时它照样全绿。 补了「真定时器 + 主动越过 2000ms」的用例后才抓住： 摘掉修复 → 该用例单独失败、原 4 条照过（1 failed | 4 passed）。

自我纠错

② 我在 buglog 里写了一句与实测相反的话

代理提交的记录写着「非 ASCII 路径隔离 worker 超时的绕行经复测未复现」。 我实测复现了（28 errors / 0 tests）。已据实更正， 并把「必须配 maxWorkers:2」及其量化依据写进记录 —— 否则下个会话会照旧记录以为「关隔离只是历史包袱、可随手打开」。

这一批我抓到的真问题里，有相当比例是「文字与实现不符」： setup.ts 声称的清理、.env.example 指错的修改文件、覆盖率门槛 70 vs 80、 SKILL.md 里 8 处不存在的路径、上一段说的 buglog。 它们都不是「代码写错了」，而是「说的和做的不是一回事」—— 而后者更难被发现，因为没人会去验证一句话。

08元教训

  1. 「无法复现」不等于「无法验证」。 我卡在「等它自然复现」，正确做法是强制构造触发条件（--no-file-parallelism 把两个文件塞进同一 worker）。
  2. 级联失败会掩盖后续问题。 修好第一层才看见第二层 —— 这既解释了「为什么修一处没用」，也提醒我别在只看到第一层时就下结论。
  3. 「文字与实现不符」是被低估的缺陷类别。 本批抓到的多数真问题属于此类，而且它们会直接把 CI 搞红。
  4. 变异测试是照妖镜。 它抓出了我两处「看起来是测试、实际没有判别力」的产物。不做的代价是：你以为有防线，其实没有。
  5. 修法的方向比修法的规模重要。 关隔离能让测试跑起来、看起来「解决了」，但那正是病根 —— 正确解法是保住隔离、让出并发。

09测验

10 道题，覆盖本批每个关键判断。展开看答案。全部答对才说明你读懂了这批变更。

Q1 · 为什么「本机 16 vCPU 跑不出 flaky」这件事本身是线索，而不是反证？

因为 flaky 的触发条件是「两个特定测试文件被分到同一个 worker」， 而文件→worker 的分配取决于哪个 worker 先空闲。vCPU 越多，文件越不容易同组。 所以「本机不复现」恰恰与「CI 上偶发」完全自洽 —— 本地跑不出，不是因为 bug 不存在，而是因为本地并发度太高，天然避开了触发条件。 推论：要复现就得人为把并发降到 1（--no-file-parallelism）。

Q2 · `vi.mock` 为什么会跨文件失效？

isolate: false 下同一 worker 内多个测试文件共享模块实例， 而 vi.mock 的假模块是按文件注册的。 后跑文件里被缓存的组件（同一个 Gallery.tsx 模块）闭包仍指向上一个文件遗留的 mock 实例， 本文件新注册的 mock 对它无效 —— 于是它拿到的是上一个文件的数据。

Q3 · 为什么「关掉 isolate」是错的方向？

因为关掉 isolate 正是跨文件 mock 串味的原因。它当时被引入是为了绕开 「非 ASCII 路径下隔离 worker 启动超时」—— 但那个绕行用正确性换了可用性。 正确解法是保住隔离、降低并发（maxWorkers: 2），让 worker 在 60s 超时前起来。

Q4 · `isolate: true` 单独改会有什么后果？

套件完全不可用：实测 28 errors / 0 tests —— 全部 worker 在 60s 内没起来。因为 isolate: true 下每个测试文件都要重启一次 worker 环境， 启动成本大幅上升，而非 ASCII 路径（2api目录）下这段本就偏慢。 所以它必须配 maxWorkers: 2 一起改。

Q5 · 进度条那个缺陷，为什么根因在「数据模型」而不是「前端」？

因为 GET /v1/tasks/{id} 的响应模型 TaskInfo 压根就没有 status_detail/progress 两个字段（DB 层也从未持久化）—— 精确阶段只有 SSE 一条路能给。前端两条路都订阅，轮询那条必然拿不到细节。 所以前端只是症状现场，根因是「服务端无法通过轮询告诉你阶段」。

Q6 · 我修的是什么，没修的又是什么？

修了「在途轮询把已知的更精确值覆盖掉」这个确定性缺陷 （用户可见的每 2 秒跳一次）。
没修「刷新页面后只剩粗粒度阶段」—— 那是精度限制，不是错误： 数据从未持久化，刷新后本来就无从得知。要修需落库 + 扩 API 契约，是独立决策。

Q7 · 为什么「加了回归测试」还得再做变异测试？

因为测试可能没有判别力。本批我第一版进度条回归锁就是伪测试： 它验证了 hook 方法本身，而缺陷在调用点 —— 把修复摘掉它照样全绿。 变异测试（把修复改回去、看测试是否真红）是唯一能证明「这条防线真的存在」的手段。

Q8 · 为什么说「CI 的失败是级联的」这个认知很关键？

因为前一步失败会让后续步骤直接 [skip] —— 你只看得见第一层。本批后端 job 的失败就是这样逐层揭开的： 先修好「单元测试」（真因是 stop() 异常打断优雅关闭）， 才暴露「集成测试」失败（真因是 test_honor 在后端 job 里必然 404）。 在只看到第一层时就下结论，会得出「修了没用」的错误判断。

Q9 · buglog 里那句被我更正的话，为什么值得单独记一笔？

因为它写的是「非 ASCII 路径隔离 worker 超时的绕行经复测未复现」—— 而我实测复现了。这条失实记录会直接误导下一个会话： 它会以为「isolate: false 只是历史包袱、可以随手打开成 true」， 然后得到 28 errors / 0 tests。已据实更正并补上「必须配 maxWorkers:2」。 记录里一句与实测相反的话，会让后来者重走一遍弯路。

Q10 · 这批最反直觉的一条元教训是什么？

「无法复现」不等于「无法验证」。
我一度把「本机复现不出」当成停手的理由，并说了「不做投机修改」—— 原则没错， 但我漏掉了第三步：主动构造触发条件（把并发降到 1，强制两个文件进同一 worker）。 一构造就复现了。
真正的判据不是「它自己有没有出现」，而是「我能不能让它出现」。
